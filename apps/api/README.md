# apps/api

API NestJS (REST + OpenAPI em `/docs`) e o processo **worker** (mesma imagem, comando `node dist/worker.js`).
Módulos por domínio: tenants, membros, empresas, contatos, atividades, oportunidades, funis, tags, prospecção, integrações.
Ver `docs/configuracao_tecnologia.md` (seções 4 e 11.3).

| `src/infra/`                                  | Conexões únicas, fechadas no encerramento: banco (`leadtogo_app`, Drizzle + postgres.js), Valkey (`ioredis`, sem fila offline) e Garage (S3 com `forcePathStyle`)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| `src/http/`                                   | `aplicarSegurancaHttp`: Helmet, CORS só para `APP_URL` (com credenciais; expõe `X-Request-Id`) e parser de corpo JSON próprio (limite 1 MB) que **pula `/v1/auth/*`**, para o Better Auth ler o corpo. `FiltroDeExcecoes`: erro padrão `{ statusCode, erro, mensagem, request_id, detalhes? }`, sem stack nem detalhe interno (500 é genérico). `ErroApi(codigo, mensagem, status)` para erros de negócio e `ZodPipe` para validar corpo, query e parâmetros                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| `src/rate-limit/`                             | Limite por IP no Valkey (`rate-limiter-flexible`, janela fixa e atômico): regra global (`RATE_LIMIT_MAX` por `RATE_LIMIT_JANELA_S`) e `@Limite({ nome, max, janelaS, falhaFechada })` por rota; `@SemLimite()` isenta (o `/health`). Estouro: `429 muitas_requisicoes` com `Retry-After`. Valkey fora: deixa passar (aviso no log), ou `503` nas rotas com `falhaFechada`. O IP vem de `X-Forwarded-For` só conforme `TRUST_PROXY` (1 em produção)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| `src/migrate.ts` · `src/migracao/`            | Entrypoint de migração (`node dist/migrate.js`, pré-deploy): `aplicarMigracoes()` do `@leadtogo/db` com `DATABASE_MIGRATION_URL`, sem o drizzle-kit. Exit 1 (mensagem curta, sem a URL) se falhar                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| `src/auth/`                                   | **Better Auth só para identidade** (sem o plugin de organizações). Montado por `toNodeHandler` em `/v1/auth/*` dentro de um controller (log, rate limit global e erros continuam valendo; o parser de corpo pula essa rota). Sessões **só no Postgres** (`auth.session`; sem `secondaryStorage` nem cookie cache), ids UUID v7, senha scrypt (mín. 10 caracteres), cadastro público desligado (contas nascem pelo primeiro acesso e pelo convite). Rate limit do Better Auth no Valkey (`customStorage`). Escrita com `Origin` diferente do front: 403. `AuthService.criarUsuarioComSenha()` cria usuários pelo servidor. **Login com Google preparado e desligado**: só existe com `LOGIN_GOOGLE=true` e as credenciais (`GOOGLE_CLIENT_ID/SECRET`; redirecionamento `<API_URL>/v1/auth/callback/google`); mesmo ligado não cria conta (`disableSignUp`), só entra quem já tem usuário. **2FA TOTP** (plugin `twoFactor`, emissor "Leadtogo"): ativar exige a senha, só vale depois de confirmar um código, o login pede o código numa segunda etapa (sem sessão até lá), 10 códigos de backup de uso único, segredo cifrado no banco; confirmar o 2FA gira a sessão; `/two-factor/verify-*` limitado a 5 tentativas por minuto |
| `src/email/`                                  | `EmailService` (nodemailer, SMTP; Mailpit em desenvolvimento) e os modelos em pt-BR (redefinir senha, confirmar e-mail). Sem `SMTP_HOST` nenhum e-mail sai (aviso no log, sem destinatário nem corpo). **Recuperação de senha**: link de 1 h e uso único, resposta igual exista ou não a conta, encerra as sessões, no máximo 3 pedidos por 5 min. **Verificação de e-mail** (`VERIFICACAO_EMAIL`, padrão ligado só em produção, que então exige SMTP): quem tenta entrar sem verificar recebe novo e-mail. `redirectTo`/`callbackURL` de fora do front são recusados (a validação do Better Auth fica ligada em qualquer `NODE_ENV`; ele a desliga em teste por padrão)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| `src/primeiro-acesso/` · `src/criar-conta.ts` | **Primeiro acesso**: `PrimeiroAcessoService` cria usuário (Better Auth), conta dona, vínculo `dono`, empresa, configurações e membro admin numa transação (CNPJ repetido desfaz tudo, inclusive o usuário). `POST /v1/primeiro-acesso` (`PRIMEIRO_ACESSO=aberto\|fechado`, fechado por padrão em produção; 5 por hora por IP, 503 sem Valkey) e `node dist/criar-conta.js` (mesmo fluxo pelo terminal, sem depender da flag; senha por prompt oculto, `CRIAR_CONTA_SENHA` ou pipe; e-mail já confirmado). Sem cadastros padrão (as tabelas ainda não existem)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| `src/acesso/`                                 | **Controle de acesso de toda rota (padrão: protegida).** `AcessoGuard` global: sessão (401), 2FA de administrador (`403 2fa_obrigatorio`, salvo `@PermiteSem2fa`), empresa ativa (`409 sem_empresa_ativa`, `403 empresa_ativa_invalida`) conferida por `app_vinculos_do_usuario`. `TenantInterceptor` abre a transação com `SET LOCAL app.tenant_id`/`app.user_id`, confere de novo sob RLS (membro ativo, empresa em teste ou ativa) e a oferece em `ContextoTenantService.db()`; se o handler falhar, desfaz tudo. Marcas: `@Publica()` (health, Better Auth, primeiro acesso), `@SemEmpresa()` (login sem empresa, ex.: `/v1/me`), `@Consolidado()` (só dono/administrador da conta, só GET, transação somente leitura, `app.tenant_ids` com todas as empresas da conta) e `@PermiteSem2fa()`. Escrita barrada pelo RLS ou pela transação somente leitura vira `403` (`acesso_negado`/`somente_leitura`), nunca 500                                                                                                                                                                                                                                                                                                           |
| `src/me/`                                     | `GET /v1/me` (usuário, empresas com o papel em cada uma, empresa ativa, `administradorDeConta`, `doisFatoresPendente`; aberto ao admin sem 2FA e sem exigir empresa ativa; lê os nomes das empresas numa transação somente leitura com `app.tenant_ids` das que ele já integra) e `POST /v1/sessao/empresa-ativa` (troca a empresa **desta sessão**; só empresa em que é membro ativo e em teste/ativa; id alheio e id inexistente dão o mesmo 403 `empresa_nao_permitida`; admin sem 2FA recebe `2fa_obrigatorio`). Tipos e schema em `@leadtogo/shared`                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| `src/health/`                                 | `GET /health` (fora do prefixo `/v1`): verifica banco (`SELECT 1`), Valkey (`PING`) e Garage (`HeadBucket`), 2 s no máximo cada. 200 com `{ status, version, checks }`; 503 se algum falhar, sem detalhes do erro na resposta (vão para o log). Usado pelo smoke test do deploy                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |

## Scripts

- `pnpm dev`: compila em modo watch e sobe API (porta `PORT`, padrão 3000) e worker com recarga, lendo o `.env` da raiz
- `pnpm build` · `pnpm start` · `pnpm start:worker` · `node dist/migrate.js` (migrações) · `node dist/criar-conta.js` (primeira conta)
- `pnpm openapi`: atualiza `openapi.json` (depois rode `pnpm --filter @leadtogo/api-client generate`)
- `pnpm test`: Vitest (SWC para os metadados de decorators do Nest). Usa o banco `leadtogo_api_test` e o Valkey `db 1` (`TEST_API_*` e `TEST_REDIS_URL` no `.env`), zerados e migrados no setup global; precisa de `pnpm dev:up`. O setup global lê `@leadtogo/db` pelo `dist`, então rode pela raiz (`pnpm test`, que compila as dependências antes) ou faça `pnpm --filter @leadtogo/db build` antes de `pnpm --filter @leadtogo/api test`.

ESM puro (`"type": "module"`): imports relativos levam a extensão `.js`.
Em runtime, os pacotes internos (`@leadtogo/db`, `@leadtogo/shared`) são lidos do `dist` deles; o `pnpm dev` da raiz compila-os antes.
